MCP와 API — AI 에이전트가 외부 시스템을 쓰는 방식

API는 소프트웨어 기능으로 들어가는 문이고, MCP는 AI에게 여러 문과 도구를 정리해서 쥐여주는 도구함이다.

핵심 관점

MCP는 API를 대체하지 않는다. API, DB, 파일, CLI, 앱 자동화 같은 실행 수단을 AI가 도구처럼 사용할 수 있게 하는 연결 계층이다.

문서 성격 발표용 개념 정리

주제 AI 에이전트가 외부 시스템을 호출하는 구조

작성 시각 2026-06-15 16:17 KST

01 · 왜 중요한가

AI 업무 자동화의 기본 구조를 이해하는 문제

기존 앱은 사람이 버튼을 누르고 앱이 API를 호출한다. AI 에이전트 구조에서는 사람이 자연어로 의도를 말하고, AI가 필요한 도구를 고른 뒤 실행 계층을 통해 외부 시스템을 호출한다.

기존 앱 구조
사용자→ 앱→ API→ 결과 화면
AI 에이전트 구조
사용자 의도→ AI Agent→ MCP / Tool Layer→ API · DB · 파일 · 앱
이 주제는 개발 용어가 아니라, AI가 실제 업무 시스템을 어떻게 사용할 수 있게 되는가에 대한 기본 구조다.

02 · API

API는 시스템 간 요청과 응답의 공식 통로

API는 한 시스템이 다른 시스템에게 데이터나 작업을 요청하는 계약이다.

예시 요청

GET /weather?city=Miami

예시 응답

{
  "temp": 84,
  "condition": "sunny"
}

API가 정의하는 것

  • 어디로 요청을 보낼지: endpoint
  • 어떤 데이터를 보낼지: request body 또는 query
  • 어떤 인증이 필요한지: token, OAuth, key
  • 어떤 작업이 수행되는지: action
  • 어떤 결과가 돌아오는지: response, JSON 등
API는 “이 기능을 쓰려면 이런 형식으로 요청하라”는 서비스의 문이다.

03 · MCP

MCP는 AI에게 도구와 맥락을 노출하는 연결 계층

MCP, Model Context Protocol은 AI 클라이언트와 에이전트가 외부 도구, 파일, 데이터베이스, 앱, 서비스에 표준 방식으로 연결되도록 해준다.

MCP가 AI에게 알려주는 것

  • 어떤 도구가 있는지
  • 그 도구가 무슨 일을 하는지
  • 입력값은 무엇이 필요한지
  • 결과는 어떤 형식으로 오는지
  • 어떤 resource/context를 읽을 수 있는지

도구 목록 예시

search_customer
create_contact
read_file
query_database
send_email
create_calendar_event
“MCP gives AI hands.” AI가 말만 하는 챗봇에서 벗어나 파일을 읽고, DB를 조회하고, 앱 기능을 호출하는 실행자로 바뀔 수 있기 때문이다.

04 · API와 MCP의 관계

MCP는 API 위에 올라갈 수 있지만, API 그 자체는 아니다

MCP는 API를 대체하지 않는다. MCP는 API를 포함한 여러 실행 수단을 AI가 도구처럼 쓰게 해주는 더 넓은 연결 계층이다.
구분 API MCP
주 사용자 앱, 서비스, 백엔드 시스템 AI client, AI agent
목적 요청을 보내고 응답을 받기 AI에게 도구와 context를 노출하기
형태 endpoint 중심 tool, resource, server 중심
예시 POST /crm/contacts create_contact tool
성격 소프트웨어 간 통신 계약 AI용 도구 연결 계층
사용자→ AI Agent→ MCP Client→ MCP Server→ REST / GraphQL API Database Files CLI / Script App Automation

05 · API가 없어도 가능한가

가능한 경우도 있지만, 실제 실행 수단은 반드시 필요하다

MCP 자체가 마법처럼 데이터를 만들거나 시스템을 제어하는 것은 아니다. MCP 서버 뒤에는 실제 실행 수단이 있어야 한다.

GraphQL API
DB 직접 연결
로컬 파일 읽기/쓰기
CLI 명령 실행

데스크톱 앱 자동화
사내 SDK
직접 작성한 코드
AI Agent
  ↓

  ↓
API / DB / File / CLI / App / Browser / SDK
“API가 없어도 MCP만 있으면 된다”는 말은 부정확하다. 정확히는 공식 API가 없어도 MCP 서버가 다른 통로를 통해 연결할 수 있다는 뜻이다.

06 · 예시

차이는 “누가 도구를 고르고 호출하는가”에 있다

예시 1 — 날씨 앱

전통적 API 흐름

사용자 → 날씨 앱 → Weather API → 날씨 데이터 → 앱 화면 표시

앱이 데이터를 직접 가져온다.

MCP 흐름

사용자 → AI Assistant → MCP weather tool → Weather API → AI 답변

AI가 데이터 소스를 도구로 사용한다.

예시 2 — CRM 연락처 생성

API 흐름

POST /crm/contacts

{
  "name": "Sofia Martinez",
  "email": "sofia@acme.com"
}

MCP 흐름

사용자: Add Sofia to CRM.

AI Agent
  → MCP CRM Server
  → create_contact tool
  → CRM API
  → contact created
API는 CRM의 기능을 노출하고, MCP는 그 기능을 AI가 안전하게 호출할 수 있는 도구로 포장한다.
예시 3 — 기업용 AI 에이전트 워크플로우

사용자 요청: “고객을 찾고, 열린 티켓을 확인하고, follow-up task를 만들고, account owner에게 이메일을 보내줘.”

1
CRM MCP Server로 고객 검색
2
Support MCP Server로 열린 티켓 조회
3
Calendar 또는 Task MCP Server로 follow-up task 생성
4
Email MCP Server로 담당자에게 이메일 발송
5
AI가 실행 결과 요약 반환
각 MCP tool은 내부적으로 하나 이상의 API를 호출할 수 있다.

07 · 초보자가 자주 하는 오해

세 가지 오해만 피하면 구조가 선명해진다

오해 1

MCP가 API를 대체한다

틀렸다. MCP는 종종 API 위에 올라가서 AI가 API 기능을 도구처럼 사용할 수 있게 한다.

오해 2

API와 MCP는 같다

틀렸다. API는 일반 소프트웨어 통신 방식이고, MCP는 AI-specific tool/context connection이다.

오해 3

AI가 마법처럼 일한다

틀렸다. 에이전트는 도구를 선택하고, 도구는 실제로 API, DB, 파일, CLI 등을 호출한다.

08 · Tool Calling과 MCP

Tool Calling은 호출 표현, MCP는 도구 제공 구조

Tool Calling

모델이나 에이전트가 “이 함수를 호출해야겠다”고 결정하고 구조화된 인자를 만들어내는 방식이다.

MCP

그 도구들을 외부 서버 형태로 표준 제공하고, AI 클라이언트가 발견·설명·실행할 수 있게 해주는 연결 규격이다.

구분 한 줄 정리
Tool calling 모델이 도구 호출을 표현하는 방식
MCP 도구를 제공하고 연결하는 표준 프로토콜/서버 구조

09 · 업무 환경에 대입하기

API는 실제 업무 기능, MCP는 AI가 그 기능을 쓰게 하는 계층

API는 실제 업무 기능

  • 생산관리앱 데이터 조회/등록 API
  • 거래명세서 OCR 저장 API
  • Google Drive, Docs, Sheets API
  • Telegram gateway API
  • UNECO backend endpoint
  • 보고서 생성/전송 endpoint

MCP는 AI용 도구 계층

  • search_obsidian_notes
  • read_drive_file
  • generate_daily_report_html
  • verify_report_in_browser
  • send_telegram_message
  • query_production_data
  • create_uneco_record
요청
  ↓
AI Agent
  ↓
MCP / tool layer
  ↓
Drive · Obsidian · Telegram · UNECO · 생산관리앱 · worker
  ↓
검수된 결과 보고
이 구조에서는 AI가 여러 시스템을 한 번에 엮어 업무 단위로 처리할 수 있다.

10 · 운영상 가장 중요한 점

강력한 연결일수록 통제된 연결이어야 한다

MCP가 강력하다는 것은 동시에 위험하다는 뜻이다. AI에게 메일 전송, 고객정보 조회, 파일 삭제, DB 수정, 외부 API 호출 같은 권한이 생길 수 있다.

생길 수 있는 권한

  • 메일 보내기
  • 고객정보 읽기
  • 파일 삭제하기
  • DB 수정하기
  • 거래처 등록하기
  • 외부 API 호출하기
  • 보고서 자동 전송하기

필수 설계

  • 읽기 전용 도구와 쓰기 도구 분리
  • 삭제, 전송, 수정은 사용자 승인
  • 권한 범위 최소화
  • OAuth/token 관리
  • 감사 로그 기록
  • 실패 시 롤백 또는 중단
  • prompt injection 방어
  • 외부 문서 지시 무시 원칙
  • tool schema 검증
  • dry-run/preview 제공
  • 최종 결과 검수
bounded worker는 제한하고, 중앙 에이전트가 API·OAuth·권한·라우팅·검수·최종 판단을 담당하는 구조가 안전하다.

11 · 안정성 기준

공식 API가 가장 안정적이고, 브라우저 자동화는 최후 수단

1
공식 API
가장 안정적이다.
2
DB 직접 연결
강력하지만 권한과 무결성에 주의해야 한다.
3
파일 기반
간단하지만 동시성과 형식 변경에 주의해야 한다.
4
CLI / SDK
좋지만 명령 안정성이 필요하다.
5
브라우저 자동화
화면 변경과 로그인 문제 때문에 최후 수단이다.
